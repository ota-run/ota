## Why This Is V12

V11 made selected-lane execution, proof, refusal, policy, replay, sandboxing, and authority more
explicit. Its refusal canaries still select tasks or workflows, and a canary may pass after any
valid runner-derived refusal. That proves the lane remains blocked. It does not prove that a named
effect would be blocked independently of the task name or another safety failure.

Effect-bound refusal assurance introduces a new semantic layer shared by contracts, policy,
execution admission, CI projection, sandbox capability output, receipts, archives, and assurance.
It is therefore a new version frame rather than another V11 implementation patch.

## Problem

A task called `drop-production-schema` may be refused because it is not agent-safe. Another task
called `maintenance` may reach the same schema mutation through a different closure and be
admitted. A task-name canary cannot establish that the effect itself is governed.

The opposite failure is also possible: a canary can report success because a missing tool,
unsupported runtime, or generic policy rule refused first. That is useful readiness evidence, but
it is not evidence that the effect policy was selected and enforced.

Ota needs to answer, within a bounded selected invocation:

- what typed effect does the executable closure declare or mechanically derive?
- which policy rules apply to that exact effect?
- did the effect policy itself refuse before any selected work or provider mutation?
- which known equivalent effect-bearing paths were actually challenged?
- which paths, opaque behavior, and out-of-Ota execution remain unproved?

## Product Boundary

V12 governs canonical effects declared by structured contract truth or mechanically derived from
typed Ota adapters. It does not infer intent from task names, shell text, comments, model output,
or an observed incident narrative.

The initial implementation is OSS and local-first. It requires no account, hosted service, bot,
or LLM. Organization policy may constrain effects through the existing policy-loading surface,
with its exact source and authority posture carried in evidence. A repository cannot authorize its
own effect or claim that repository-controlled policy is independently administered.

Ota does not claim:

- that every real-world side effect was discovered;
- that a declared effect occurred successfully;
- that a refused task would otherwise have produced the declared effect;
- that command strings or opaque scripts have been semantically analyzed;
- that raw shell outside Ota is controlled;
- that application correctness, database rollback, or external-system consistency was proved.

## Canonical Effect Model

### Effect definition and attachment

The contract gains a versioned catalog of reusable effect definitions. Tasks and typed adapter
steps attach definitions by contract-local reference. The reference is an authoring locator; it is
not authority and is excluded from the effect's semantic identity.

Initial activated shape:

```yaml
resource_bindings:
  production_primary:
    kind: database
    provider: postgresql
    namespace:
      authority: dns:example.org
      environment: production
      tenant: platform
      account: primary

effect_definitions:
  production_schema_migration:
    kind: database_schema_mutation
    action: apply_migration_set
    resource:
      engine: postgresql
      target_ref: production_primary
      schema: public
    bounds:
      migration_set:
        root: migrations
        content_identity: sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
      start_state: any_within_set

tasks:
  db:migrate:
    effects:
      declared:
        - production_schema_migration
```

The public schema may grow through versioned additive branches, but it must preserve these rules:

- effect definitions are immutable semantic values within one contract snapshot;
- unknown fields refuse validation rather than disappearing from identity;
- duplicate normalized definitions may share one effect identity while retaining every origin;
- task names, workflow names, display labels, and definition labels do not alter effect identity;
- every attachment retains its exact invocation and closure path as origin evidence;
- recursive dependencies, aggregates, outcome hooks, proof helpers, lifecycle assertions, and
  selected services participate whenever they can execute;
- free-form or secret-derived resource identity never becomes a public digest of the secret;
  unresolved identity makes the effect incomplete and therefore unavailable for positive
  assurance.

### Effect and realization identity

Effect equivalence and realization provenance are separate identities.

One canonical `EffectIdentity` contains only consequence truth:

```text
schema version
effect kind
typed action
canonical ResourceBindingIdentity
normalized bounds
```

One canonical `EffectRealizationIdentity` contains:

```text
effect identity
derivation posture
adapter and profile identity
application-plan identity when mechanically derived
resource-binding evidence identity and authority posture
exact invocation origin and closure path
```

Both use separate fixed RFC-8785/JCS SHA-256 domains. Self-identity fields, contract-local labels,
task names, and machine paths are excluded from `EffectIdentity`. Resource paths are normalized
relative to the contract root where applicable. Credentials and resolved secret values are never
serialized.

Canaries and equivalent-path discovery compare `EffectIdentity`. Assurance eligibility evaluates
the corresponding realization identities. Two adapters that express the same kind, action,
resource, and bounds share one effect identity; they remain distinct realizations with independent
eligibility and evidence.

Each task attachment also has an `EffectAttachmentIdentity` derived from its normalized contract
subject/path and resolved effect identity. It is not part of effect equivalence. It gives canaries
and receipts a stable way to bind one exact origin and realization without borrowing evidence from
another path carrying the same consequence.

### Resource binding identity

A contract-local `target_ref` is only a lookup label and never identifies a real resource by
itself. It resolves to one canonical, non-secret `ResourceBindingIdentity` containing:

```text
schema version
resource kind and provider
globally qualified namespace authority
ordered account, organization, tenant, environment, region, cluster, repository, or equivalent
provider-specific non-secret canonical resource identifier when available
```

The namespace authority is explicit. The initial profile uses an organization-controlled
lowercase `dns:` authority; future profiles may add separately versioned URI or provider-owned
authority branches. Ota rejects ambiguous bare aliases. Every initial namespace component and
provider-specific resource identifier uses the exact versioned ASCII profile
`[A-Za-z0-9][A-Za-z0-9._:/+=,-]{0,255}` rather than Unicode normalization. Irrelevant or
contradictory fields are forbidden. A policy wildcard is an explicit selector over resolved
identities, never an omitted identity component.

`ResourceBindingEvidence` separately records how that identity was obtained:

- `repository_declared`;
- `policy_bound`;
- `provider_verified`.

The evidence posture does not change the resource or effect identity. It changes realization and
assurance strength. Missing namespace authority, unresolved binding, secret-only identity, or a
conflict between contract, policy, and provider truth makes the effect incomplete. A repository
declaration can support bounded repository-owned enforcement, but it cannot imply independently
administered or provider-verified resource authority.

The selected invocation separately binds:

- contract snapshot identity;
- ordered execution graph and every effect origin;
- Ota-observed `agent | non_agent` invocation posture without inferring a richer actor identity;
- workflow instance, task inputs that can be identified safely, execution mode, lifecycle,
  platform, backend/provider, services, hooks, and runtime overrides;
- the ordered canonical effect-identity set and realization-identity set.

Two differently named tasks that resolve to the same normalized effect receive the same effect
identity but different selected-invocation identities and origin paths.

### Derivation posture

Every realization carries one of these derivation postures:

| Posture | Meaning |
| --- | --- |
| `typed_derived` | A typed Ota action or adapter mechanically emits the complete effect. |
| `declared_and_typed` | A contract definition is reconciled with a typed adapter application plan. |
| `declared_only` | The contract declares an effect around an opaque command or provider path. |
| `incomplete` | Action, resource, destination, bounds, or origin identity cannot be resolved. |
| `opaque` | The selected path can execute behavior Ota does not semantically model. |

Policy may deny any posture conservatively. Positive effect-refusal assurance initially requires
`typed_derived` or `declared_and_typed`. A `declared_only`, `incomplete`, or `opaque` path cannot be
promoted into supported assurance merely because it was refused.

## First Effect Family: Deterministic Schema Mutation

The first shipped family is `database_schema_mutation`. Its initial action set is deliberately
bounded:

- `apply_migration_set`;
- `rollback_migration_set`;
- `reset_schema`.

The resource identity includes the resolved database `ResourceBindingIdentity` and a normalized
schema/database selector. A bare logical target reference is insufficient. Ota does not claim to
parse arbitrary SQL into object-level effects. The effect is bounded to one exact typed action,
resolved resource, and action-specific bound set.

Schema-mutation bounds are a discriminated union selected by `action`; unknown fields and fields
from another action branch refuse schema validation:

| Action | Required bounds | Forbidden bounds |
| --- | --- | --- |
| `apply_migration_set` | content-addressed root-relative `migration_set`; explicit `start_state` as `any_within_set` or one exact state identity | rollback target; reset scope; post-reset action |
| `rollback_migration_set` | content-addressed `migration_set`; exact `target_migration_identity`; explicit `start_state` | reset scope; post-reset action |
| `reset_schema` | exact `reset_scope: schema`; `post_reset` as `empty` or `apply_migration_set` | rollback target; apply/rollback start-state fields outside the nested post-reset branch |

`post_reset: apply_migration_set` requires its own content-addressed migration set. Optional fields
are explicit inside their action branch and participate in identity; omission never imports a
field from another branch. The action discriminator already encodes apply versus rollback
direction; a separate `direction` field is forbidden so equivalent effects cannot split between
redundant representations. Migration roots must be exact alias-free slash-separated paths as
authored; repeated or trailing separators and `.` or `..` components refuse instead of being
normalized before identity derivation. Controls and Unicode line separators are outside the path
character profile and refuse in both contract validation and published schema admission.

The first adapter must be a typed task body with a deterministic application plan. Wrapping
`psql`, `prisma migrate`, `rails db:migrate`, or another tool in opaque shell does not become typed
evidence through command-name recognition. Unsupported engines, dynamic targets, interpolated
migration roots, unbounded command arguments, or provider-owned migration behavior remain
`declared_only`, `incomplete`, or `opaque` and fail positive assurance.

The typed adapter produces one content-addressed `EffectApplicationPlan` from the selected
invocation, resource binding, migration-set manifest where applicable, and discriminated bounds.
The realization is derived from that plan, whose canonical discriminated action payload contains
every action-specific bound needed by the executor. The executor receives that exact plan rather
than rereading the contract or reconstructing a parallel command. Immediately before allowed execution, Ota
re-observes resource-binding and migration-set inputs and re-derives the plan; drift refuses before
provider contact. Provider/application evidence binds the exact delivered plan identity. Core can
prove ordered byte delivery to the selected adapter boundary; provider evidence must separately
prove what the adapter did after delivery. This does not prove database correctness or successful
schema mutation.

Later families may add:

- `mass_communication` with channel, audience/destination, message-source identity, and recipient
  bounds;
- `external_data_mutation` with provider, action, resource collection, and record/object bounds.

Those families are not part of the first completion bar. Each requires its own typed adapter,
policy selectors, schemas, archive rules, and independent pressure before it can produce
supported assurance.

## Effect Policy

The existing policy-pack authority is extended with typed effect selectors. A rule may constrain:

- effect kind;
- action;
- resource provider/type and canonical resource binding or explicit typed namespace pattern;
- normalized bounds;
- derivation posture;
- selected task/workflow subjects when an additional narrowing is required.

Provisional policy shape:

```yaml
effects:
  typed:
    rules:
      - id: deny_production_schema_mutation
        selector:
          kind: database_schema_mutation
          actions: [apply_migration_set, reset_schema, rollback_migration_set]
          resource:
            match: exact
            engine: postgresql
            namespace:
              authority: dns:example.org
              environment: production
              tenant: platform
              account: primary
        decision: deny
```

Rule IDs are unique within one policy snapshot. Unknown selectors and duplicate normalized rule
IDs refuse contextually while that policy is active. All matching rules accumulate; specificity or
document order never discards a broader restriction. The aggregate result follows precedence and
retains every applicable rule identity.

Resource selection is a strict tagged branch: `match: exact` carries one complete canonical
binding, `match: namespace_pattern` carries explicit typed wildcard positions, and `match: any`
matches every resolved resource of the selected kind. Omitted fields are never implicit wildcards,
and `"*"` matches only a present dimension. Typed selector lists are unique ascending semantic sets
so their authored form and policy-rule identity cannot diverge.
and no selector can match an unresolved resource identity for positive assurance.

The evaluator loads one command-scoped policy snapshot and computes one immutable decision before
provisioning, task execution, hooks, services, proof artifacts, or provider mutation. Typed rules
use the shipped `allow | warn | deny` vocabulary. They do not introduce `review` into the effect
domain. Every applicable rule identity and ground is retained.

The snapshot alone does not prove who controlled it. One canonical `PolicySourceEvidence` binds:

```text
policy snapshot identity
source kind: env_override | repository_policy | workspace_policy | independently_prebound
redacted source-location identity
authority posture: caller_selected | repository_controlled | workspace_controlled |
                   independently_administered
source-verification evidence when the posture is stronger than workspace_controlled
```

Current `OTA_POLICY` selection is `caller_selected`; `.ota/org-policy.yaml` is
`repository_controlled`; workspace discovery is `workspace_controlled`. A file path, URL, root
ownership claim, or policy self-annotation never upgrades that posture. A future
`independently_prebound` source requires its own fixed discovery, integrity, and authority proof.
The same policy content loaded from different source/authority postures has different decision
evidence even though its policy snapshot identity is unchanged.

Operational effect enforcement remains real under every recorded posture. V11.14 assurance and
public output must carry that posture and may not describe repository- or caller-controlled policy
as independently administered governance. A policy or claim profile may require a minimum source
posture; insufficient posture refuses or remains `unknown` according to that existing policy
domain and cannot be repaired by a canary.

One restrictive lattice composes the current coarse effect rules, safe-task fallback, policy mode,
typed rules, and caller overrides:

1. Existing coarse selectors are evaluated exactly as shipped, including `effects.safe_tasks`
   falling back to `effects.tasks`.
2. Explicit typed rules are evaluated independently and all matches accumulate.
3. When no explicit typed rule matches, the existing `effects.mode` supplies the typed fallback:
   `compatibility` is `warn`; `strict` is `deny`.
4. Existing `--effect-override` values continue to affect only their shipped coarse selectors.
   They are bound to the selected invocation but cannot target or replace a typed rule or typed
   fallback.
5. The final decision is the most restrictive decision across every component:

```text
deny > warn > allow
```

No specificity, document order, task-safe fallback, or caller override can discard a more
restrictive component. A caller override may preserve its current compatibility behavior for a
coarse effect but cannot weaken a typed `deny` or make an effect-refusal canary pass. A canary
requires an explicit matching typed rule with `decision: deny`; strict-mode fallback, legacy
coarse denial, or caller override alone is insufficient positive assurance.

`review` from claim-assurance, replay-input, or another existing policy domain remains a separate
refusing ground and never becomes an effect decision. A future effect-approval carrier would
require a separate reviewed design. Ordinary crossing authority cannot alter the aggregate effect
decision or turn unknown/incomplete effect truth into an allow. A repository effect definition
supplies execution truth only; it cannot supply policy, approval, issuer identity, or an expected
decision.

The canonical `EffectPolicyDecision` binds:

- command-scoped policy snapshot identity;
- policy-source evidence identity and authority posture;
- selected invocation and execution-graph identities;
- canonical effect-set and realization-set identities;
- each applicable effect, eligible/ineligible realization, and origin path;
- every applicable rule identity and decision basis;
- aggregate decision and precedence result;
- evaluation version.

Invalid policy, unknown selectors, incomplete mandatory identity, or inconsistent effect origins
fail closed before side effects. Existing unconditional hard-pin, authority, or runtime-validation
failures remain unconditional and cannot be downgraded by effect policy.

## Effect-Based Refusal Canaries

V11.3 lane refusal canaries remain valid for their original claim: the selected lane was refused
before execution. V12 adds a separate effect-bound canary and does not silently change the meaning
of existing canaries.

Provisional shape:

```yaml
agent:
  effect_refusal_canaries:
    - id: production_schema_refusal
      effect: production_schema_migration
      challenge_lanes:
        - task: db:migrate
          origin:
            task: db:migrate
            effect: production_schema_migration
        - task: maintenance:migrate
          origin:
            task: maintenance:migrate
            effect: production_schema_migration
        - workflow: release
          origin:
            task: db:migrate
            effect: production_schema_migration
```

Each challenge lane is one exact selected invocation. A canary passes only when:

1. the selected closure contains the referenced canonical effect identity;
2. the required origin resolves to one exact effect attachment and realization identity;
3. that exact challenged realization has a posture eligible for assurance;
4. the shared effect evaluator returns an independently sufficient `deny` ground from an explicit
   typed rule for that effect and identifies the applicable policy rule set;
5. refusal occurs before provider, repository, service, hook, child-process, or task mutation;
6. the emitted refusal evidence binds the expected effect, exact attachment/realization, exact
   lane, policy snapshot, rule identities, and `execution_started: false`.

A canary may retain other independently derived refusal grounds, but those grounds cannot
substitute for the exact effect denial. A canary does not pass when:

- generic agent safety, missing tooling, readiness, authority, runtime, or sandbox refusal occurs
  first;
- the effect is absent from the selected closure;
- the requested origin is absent, duplicated, ambiguous, or resolves to another realization;
- the effect is only declared around opaque behavior;
- typed policy evaluates `allow` or `warn`, or only a fallback/legacy rule denies, rather than an
  explicit typed effect denial;
- execution or provider mutation begins;
- evidence cannot identify the exact effect-policy decision.

Those outcomes are typed as `not_evaluated`, `assurance_gap`, or `failed` rather than being
reported as a successful negative control. The evidence retains both the actual blocking reason
and why effect refusal was not established.

Challenge lanes use the contract's canonical execution selection unless the canary records a
typed, non-secret workflow instance or bounded input value explicitly. The `origin` is mandatory
and names one effect attachment reachable in that exact selected closure; eligibility from another
attachment with the same effect identity cannot satisfy it. Free-form values, secret values,
ambient environment, or caller-supplied overrides make the challenge identity incomplete and
therefore ineligible for positive assurance. A caller cannot widen the recorded challenge
selection at invocation time.

The canary `id` is a contract-local invocation locator, not effect identity or policy authority.
Contract validation requires unique IDs and at most one challenge entry for each normalized
`(canary id, selected lane)` pair. The semantic canary identity binds the resolved effect,
attachment, realization, selected invocation, and policy requirement; renaming the locator alone
does not change those identities.

### Command and exit semantics

The first public invocation stays on the existing runner surfaces:

```text
ota run --agent --expect-effect-refusal production_schema_refusal --json db:migrate
ota up --workflow release --agent --expect-effect-refusal production_schema_refusal --json
```

`--expect-effect-refusal` is an Ota flag before the repo-level positional task/path/input tail; the
workflow form follows `--workflow`. Its value is a predeclared canary ID, not an effect reference or
origin supplied by the caller. Ota resolves that ID plus the exact selected lane to one stored challenge entry, then uses
the entry's mandatory origin to resolve one attachment and realization. Unknown IDs, a lane not
declared under that ID, or zero/multiple normalized challenge matches refuse as `not_evaluated`
before effect evaluation. The command never guesses an origin and never accepts a caller-authored
expected rule, decision, reason, effect, attachment, or realization.

The operational result is:

| Status | Meaning | Exit |
| --- | --- | --- |
| `passed` | Exact eligible effect and policy denial were established before side effects. | `0` |
| `not_evaluated` | Structural, availability, or authority refusal prevented effect evaluation. | non-zero |
| `assurance_gap` | Effect is absent, opaque, incomplete, or otherwise ineligible. | non-zero |
| `failed` | Policy did not deny, the expectation mismatched, or execution/provider mutation began. | non-zero |

If the selected lane is admitted, the expectation fails before selected execution rather than
running a potentially dangerous lane to demonstrate failure. Canary invocation is already
execution-free and cannot be combined with `--dry-run`; it must reconcile with the same decision
derived by ordinary preview and execution admission. Neither path may create selected-lane effects.
Existing `--expect-refusal` behavior and JSON remain unchanged.

## Shared Enforcement Surface

One domain evaluator below CLI orchestration must drive:

- `ota run` dry-run and real execution;
- `ota up` dry-run and real execution;
- task and workflow effect-refusal canaries;
- Doctor/preflight diagnostics without execution;
- provider-neutral CI projection and provider-side re-evaluation;
- sandbox policy/capability compilation and provider admission;
- governance JSON, receipts, and archive verification.

No surface may reconstruct effect policy from formatted output, reload policy independently, use a
dependency-only closure, or substitute a render-checkout verdict for provider-checkout runtime
truth. CI carries semantic requirements, effect/rule identities, and expected canary posture; it
re-evaluates the actual checkout before execution.

Sandbox output may say that a declared effect was policy-denied within the selected Ota lane. It
must not imply syscall-level mediation, host-wide isolation, prevention outside Ota, or application
correctness.

## Assurance and Coverage Honesty

V12 extends V11.14 with one canonical claim family: `effect_refusal_assurance`. It reuses the
existing machine status taxonomy:

- `supported`: every named challenge lane was refused by the exact effect policy with eligible
  typed effect evidence;
- `contradicted`: a named challenge lane was admitted, began execution, or produced evidence
  inconsistent with the claimed effect-policy denial;
- `unknown`: required effect identity, eligible derivation posture, policy evidence, or challenge
  execution is absent or incomplete.

Canary execution outcomes remain operational evidence and are not a second assurance taxonomy.
Human wording may explain a supported or bounded result but must preserve the canonical machine
status. `supported` is bounded to the explicitly named challenge set and may coexist with
`not_proved` entries; it is never a repository-global effect-prevention claim.

Coverage records include:

- tested selected invocation identities and origin paths;
- exact challenged attachment and realization identities;
- known contract paths that carry the same canonical effect identity but were not challenged;
- policy source/authority, effect, and realization identities used by each challenge;
- opaque or incomplete selected paths;
- the contract snapshot and discovery scope used to enumerate known paths.

When a known effect-bearing path is not tested, Ota emits
`equivalent_execution_paths_not_proved`. Equivalence means exact canonical effect identity in the
typed contract graph. Ota does not infer semantic equivalence from names or shell bodies.

When shell, scripts, provider configuration, or direct external operations could perform an
effect but Ota cannot enumerate them, it emits an opaque-path boundary such as
`opaque_execution_paths_not_enumerated`. Absence from the known graph is never evidence that no
equivalent path exists.

An undeclared or opaque effect is `unknown`. It is `contradicted` only when canonical evidence
conflicts with an explicit claim, such as a named canary lane executing after the claimed denial.

## Receipts and Archive Verification

The first shipped carrier is deliberately narrow. A non-dry-run `ota up` receipt blocked by an
explicit typed policy deny retains `typed_effect_policy_refusal` with the exact command-scoped
decision and `execution_started: false`; ordinary refusal remains non-durable. Explicit
`ota up --workflow <name> --archive-effect-refusal --json` creates one create-new negative receipt
archive. It retains one private immutable policy snapshot alongside the existing immutable contract
snapshot. A decision identity alone is insufficient: history parses the retained policy bytes,
verifies their snapshot identity and source posture, re-derives the selected invocation and typed
plans from the archived contract, and recomputes the decision. Archive admission refuses when the
policy bytes cannot be retained and re-read without aliases, when the selected invocation is
incomplete, or when the record is only a fallback, coarse, unavailable, or provider-disabled
refusal. This private archive carrier is not a public export profile; later export must apply its own
disclosure rules. Atomic publication followed by directory-sync failure is a distinct
`published: true`, durability-uncertain outcome carrying the exact archive path and recovery
guidance. It must never collapse into an ordinary pre-publication failure.
Snapshot publication uncertainty is a separate partial-transaction outcome: it names
`policy_snapshot` or `contract_snapshot`, carries the exact path, and states that no refusal receipt
was published by that attempt.

Effect-refusal canary output remains execution-free and ephemeral. Doctor may consume the existing
verified private refusal archive without introducing a second archive format, but only for an exact
workflow challenge lane: the current semantic contract snapshot, workflow, eligible effect,
attachment, realization, explicit typed deny, and pre-execution posture must all reconcile. A
task-only challenge remains `unknown` until a durable task carrier exists. It must not archive a
standalone `passed` canary or promote fallback, coarse, unavailable, or provider-disabled refusal.
An invalid sibling archive or more than one exact matching archive leaves the claim `unknown`:
Doctor never chooses attestation evidence by archive order.

The later durable refusal/archive and successful assurance records must bind:

- effect and effect-set identities;
- selected invocation, graph, and origin paths;
- command-scoped policy snapshot, policy-source evidence/authority posture, and applicable rule
  identities;
- exact effect-policy decision and refusal reason;
- execution-attempted posture and pre-side-effect observations;
- tested-path coverage and every `not_proved` boundary.

Archive verification re-derives the effect graph from the archived contract snapshot and exact
selected invocation, loads only the archived policy-authority snapshot permitted by the existing
archive model, verifies its recorded source/authority evidence, and recomputes
effect/realization/rule/decision/coverage identities. Removing an effect, changing a resource or
bound, substituting source authority or generic refusal, altering a challenge lane, or stripping
coverage boundaries invalidates the archive. Independently administered posture is valid only
when the archived authority evidence re-verifies; an archived label is insufficient.

Local content addressing remains internal reconciliation, not tamper-proof storage against a
same-user rewrite. Stronger storage or signer claims require their own authority.

## Incident Ratchet and Reviewed Candidates

A receipt or incident artifact may propose an effect definition or effect-refusal canary. It never
edits a contract or policy directly.

V12 must reuse V11.22's shared reviewed-candidate envelope, identity, source re-observation,
re-derivation, collision protection, dry-run, and atomic application path. It must not create a
second mutation authority. Because V11.22 v1 admits only `detection | upgrade`, V12 introduces an
explicit additive candidate-schema v2 branch:

```text
candidate kind: effect_assurance
registered derivation profile: effect_assurance_v1
allowed operation: add
```

V1 detection/upgrade artifacts retain their original identity and behavior. Pre-V12 readers reject
the new kind as unsupported; they never reinterpret it as detection or upgrade. The v2 branch
shares V11.22 admission/application internals but has its own strict schema, derivation profile,
and add-only operation rules.

The effect/canary candidate is add-only in this slice and binds:

- source receipt/archive or incident-artifact identity and provenance posture;
- contract snapshot and selected invocation identity;
- proposed effect definition and typed origins;
- proposed resource binding plus its evidence and authority posture;
- proposed challenge lanes;
- residual unknown, opaque, and equivalent-path gaps;
- exact candidate derivation implementation identity.

Receipts are evidence only for fields they actually carry. An operator-authored incident is
untrusted context unless independently signed by a supported authority; it may still seed a
review candidate but cannot establish that an effect occurred. Re-observing the same incident
narrative establishes reproducibility only, not authority or an `applicable` disposition.

An incident-only candidate remains `unknown`, review-only, and ineligible for contract write.
V11.22 application may write a proposed effect or canary only when each written subject is
`applicable` because independently deterministic typed repository evidence re-derives it, or a
verified archive already carries those exact canonical fields and the current typed graph
reconciles them. Candidate application re-verifies the source archive where available,
re-observes repository evidence, re-derives the current effect graph, and refuses stale,
conflicting, incomplete, non-reproducible, or incident-only proposals.

Candidates never propose effect-policy `allow`, approval, grant, or trust-root changes. Removal or
weakening requires a separately reviewed semantic migration or maintainer-authored change outside
the incident ratchet.

## Acceptance Bar

- the same typed effect in two differently named tasks receives one effect identity while
  retaining both invocation origins;
- two typed adapters expressing the same kind, action, resource, and bounds share one effect
  identity while retaining distinct realization identities and eligibility evidence;
- effect identity changes when kind, action, resource binding, destination, discriminated bounds,
  or migration-set content changes; adapter/profile, derivation posture, application plan, or
  origin changes realization identity without splitting an otherwise equal effect;
- bare target labels, unresolved namespace authority, or conflicting resource-binding evidence
  make the effect incomplete; policy wildcard matching remains an explicit selector rather than an
  identity omission;
- an allowed typed-adapter control receives the exact admitted `EffectApplicationPlan`, including
  canonical action-specific bounds, and every ordered retained migration byte; immediate source or
  plan substitution and disconnected or failing delivery refuse before provider contact; Core does
  not claim to prove what an in-process callback does after delivery;
- task/workflow labels, machine paths, timestamps, and contract-local effect labels do not change
  semantic effect identity;
- unresolved secret-derived or free-form resource truth becomes incomplete without exposing or
  hashing secret values into public evidence;
- dependencies, aggregates, outcome hooks, lifecycle assertions, services, proof helpers, and
  selected runtime overrides contribute to the complete effect graph when executable;
- one command-scoped policy snapshot drives dry-run, real execution, Doctor/preflight, receipts,
  and provider projection without mixed authority;
- policy source kind, authority posture, and verification evidence are identity-bound across
  decisions, receipts, coverage, and archives; identical policy content from caller, repository,
  workspace, or independently administered sources cannot be presented as the same authority;
- coarse rules, safe-task fallback, typed rules, policy-mode fallback, and existing caller
  overrides compose through `deny > warn > allow`, with every component inspectable;
- caller overrides cannot weaken typed denial, count as explicit typed canary authority, or make a
  canary pass;
- a crossing grant cannot bypass effect denial or convert incomplete effect truth into allow;
- `run`, `up`, CI provider re-evaluation, sandbox output, and canaries produce the same effect
  decision for the same contract, policy, and selected invocation;
- refusal occurs before task, hook, service, child-process, repository, provider, or external-state
  mutation;
- a canary refused for generic safety, missing readiness, unsupported runtime, or authority failure
  does not pass effect-refusal assurance;
- an eligible realization cannot satisfy a challenge bound to an ineligible realization carrying
  the same effect identity; absent, ambiguous, or substituted origin identity is an assurance gap;
- public canary invocation resolves one predeclared canary ID and exact selected lane to one stored
  attachment/realization; unknown, undeclared-lane, duplicate, or ambiguous matches refuse without
  origin inference;
- a task or workflow omitting the named effect returns an assurance gap, not a protected claim;
- `declared_only`, `incomplete`, and `opaque` effects cannot produce supported assurance;
- known untested equal-effect paths emit `equivalent_execution_paths_not_proved`;
- unenumerable shell/provider paths retain an explicit opaque-path boundary;
- V11.14 machine output uses only `supported | contradicted | unknown` for the new claim family;
- receipts and archives reject removed effects, changed bounds, substituted policy/refusal
  evidence, incomplete origin graphs, and stripped coverage boundaries;
- `effect_assurance` candidates use a strict additive candidate-schema v2 branch and registered
  derivation profile while reusing V11.22 admission/application authority;
- incident-derived candidates are reviewable, add-only, stale-safe, reproducible, and applied only
  through the V11.22 candidate authority;
- incident-only proposals remain `unknown` and non-writable; write eligibility requires V11.22
  `applicable` evidence from deterministic typed truth or an exactly reconciled verified archive;
- no candidate can alter policy, approval, grant, issuer, or trust-root truth;
- schemas and JSON conformance reject contradictory decision, coverage, derivation, and archive
  states;
- public documentation states selected-lane scope and raw-shell/provider boundaries without
  implying global effect prevention.

## Explicit Non-Goals

- universal syscall, SQL, API, data-flow, or semantic program analysis;
- inferring effect equivalence from task names, shell strings, logs, or model intent;
- automatically adding, removing, approving, or weakening contract or policy truth;
- policy-managed accounts, dashboards, billing, bots, or hosted approval services;
- proving application correctness, successful rollback, recipient consent, or data integrity;
- controlling commands executed outside Ota;
- shipping `mass_communication` or `external_data_mutation` before each has a typed adapter and
  independent acceptance proof.
